# Changelog

All notable changes to the Variorum specification. Format loosely based on Keep a Changelog; the specification follows SemVer (see [GOVERNANCE.md](GOVERNANCE.md)).

## [Unreleased]

### Added

- **`REC-23` and `REC-24`** — a generator with several textual fields now has a place to say which one `recipe.prompt` holds. `recipe.promptField` names it in the provider's own vocabulary (`"lyrics"`, `"styles"`); `REC-23` is a SHOULD for the generator that accepts more than one textual field, and `REC-24` a MUST on the member's shape — a non-empty string that cannot appear without `prompt`. The case is Suno's Custom mode: six textual fields, no box called "prompt", and an API that reuses the name for the lyrics field. The `echo-language` adopter put the lyric field in `prompt` and the rest in `parameters`, which was defensible and unstated; `"promptField": "lyrics"` is what makes the reading checkable by a reader who has never seen Suno's interface.
- `spec/vectors/recipe.json` — four vectors: an accept for a named multi-field prompt (`REC-9`, `REC-23`, `REC-24`), and rejects for a non-string, an empty and an orphaned `promptField` (`REC-24`). The suite moves to 208 vectors in thirteen groups; coverage to 102/142 rules referenced, 40 exempt, 0 uncovered.
- `docs/adr/ADR-0016-the-prompt-is-one-field-and-the-record-names-it.md` — the four options (an object of named fields, the provider's literal `prompt` field, a semantic winner defined in the rule, one string with a declared field name), why the object duplicates `parameters` and repeats the split ADR-0015 refused, why the provider's literal name moves the standard's answer with the vendor, and why an absent `promptField` means an unspecified mapping and not "the generator has one field".
- `REC-24` in the reference validator (`TOOL_VERSION` 0.9.0), for a recipe and for every hybrid stage (`REC-19`). `tests/test_validate.py` gains four tests, one of which pins that an unnamed prompt draws no warning: `REC-23` is a SHOULD and the validator cannot see the provider's interface.
- **`REC-12` gains a fourth determinism grade, `content`,** for the recipe that fixes every vertex and no byte. The gap was measured by the `3d-printerator` case study: one OpenSCAD source, one toolchain, three builds with the same 7,492 triangles and three different digests, because the facet order varies between runs. `full` was forbidden by `REC-13` and `none` denied a determinism that is real, so the record omitted the member and the absence was indistinguishable from a producer who never considered the question. The four grades are now defined in a table rather than listed — `none`, `seeded`, `content`, `full` — and `REC-13` requires a verified re-execution for a `content` claim exactly as it already did for `full`. `REC-12` stays a SHOULD: an unrecognised grade is a warning, never a rejection (`CON-8`), because a closed vocabulary that punished the unforeseen case is how the need for `content` arose.
- **`REC-22`** — a record claiming `determinism: "content"` SHOULD state the normalization under which two executions are compared, as a non-empty string in `parameters.normalization` on the object that carries the claim (the recipe, or a hybrid stage; for example `"binary STL: the multiset of triangles, facet order ignored"`). The digest cannot stand in for it: two files that hold the same geometry have different digests by construction, so a consumer who compared digests would report a correct recipe as irreproducible.
- `spec/vectors/recipe.json` — three vectors: a `content` claim with its normalization (accept, `REC-12` and `REC-22`), one without it (accept, `REC-22` — a warning, not an invalidation), and an unrecognised grade (accept, `REC-12` — the guard against a validator that turns the SHOULD into a MUST). The suite moves to 204 vectors in thirteen groups; coverage to 100/140 rules referenced, 40 exempt, 0 uncovered.
- `docs/adr/ADR-0015-a-recipe-can-determine-the-content-not-the-bytes.md` — the four options (leave the member alone, `geometry`, `content`, split the member into grade and basis), the measurement that forced the question, and why `content` is a grade of the output rather than a domain word.
- `tests/test_schema.py` — the schema and the tool had never been compared. `SchemaVocabularyTests` pins every closed vocabulary they share (recipe kinds, the seven states in all three places they appear, the eight lineage relations, actor kinds, signature algorithms, the four conformance classes and the five typed bridge claims) and fails if `recipe.determinism` grows a `type` or an `enum`.
- `spec/90-extensions/prov.md` — the fifth extension bridge (`PROV-1`…`PROV-6`), and the first that is not a pointer. PROV hands out no document identity — a PROV document is "an anonymous instance, called the toplevel instance, together with zero or more named instances, called bundles" (PROV-CONSTRAINTS §1.2), it need not be valid, and the five reserved attributes it defines include none that hashes bytes (§5.7.2) — so the claim is one member, `extensions["variorum:prov"].version` = `"2013"`, the date the family was recommended, because PROV was published once and has no edition number. What the claim buys is a member-by-member projection (§90.3): `id` becomes the artifact's `prov:Entity` identifier, `lineage.parents[]` becomes `prov:wasDerivedFrom` with `prov:type` naming the relation, `recipe` becomes an activity with its tool as `prov:SoftwareAgent` and its prompt optionally a `prov:Plan`, and `state.transitions[]` becomes one activity per decision. Two rows carry the weight: `created` and `producer` describe the *record*, not the artifact, so they attach to the bundle and never to the entity (90.4) — projecting `created` onto the entity would date the 2002 installer of the `software-tools` case study to 2026, and `prov:wasAttributedTo(entity, archive)` would say the archive built the binary. And Variorum's `generation` relation is not PROV's Generation event: the former is `prov:wasDerivedFrom` with a type, never `prov:wasGeneratedBy` (90.5). Identity stays material: `id` makes PROV's nominal identity carry the digest, no PROV identifier or blank node becomes an `id`, and `alternateOf`/`specializationOf` are refused as lineage because PROV says they are not influences (§5.5.1, §5.5.2) (90.6). `PROV-4`…`PROV-6` bind a consumer holding a graph and are exempted. Every citation was checked against PROV-DM, PROV-O and PROV-CONSTRAINTS before merging, and one quotation inherited from the draft was wrong: §5.5.2 says alternates "present aspects of the same thing", not the words the draft had put in its mouth.
- `spec/vectors/prov.json` — 12 vectors for the bridge, each marked `"bridge": "variorum:prov"`, including reject vectors for a claim that is a string, `null`, an array, empty, `"2.0"` or the number `2013`, and for a `document`, an `entity` or a `checksum` smuggled into the claim; accept vectors for the one-member claim, for a record carrying every section the projection names at once, and for a record whose `scheme.name` is literally `prov` with no claim at all — a bridge that fired on a name would make `core` stricter than `SCH-7` allows (ADR-0009). The suite's totals move to 200 vectors in thirteen groups.
- `docs/adr/ADR-0014-prov-bridge-is-a-profile-not-a-pointer.md` — the four candidate shapes (pointer, embed, profile, no bridge) and why only the profile survives: a `document` member would be a URI no rule can distinguish from a typo and no reader can resolve, a `checksum` would either duplicate the digest or carry a value with no subject, and embedding an entity/activity/relation model would give the record two grammars to keep in step with no test to compare them.
- `PROV-1`…`PROV-3` in the reference validator (`validate_prov_bridge`, `PROV` rule family); `TOOL_VERSION` 0.7.0.
- `docs/case-studies/echo-language.md` — the third Phase 3 case study, and the first artifact in this project produced by a model. The project is Echo Language, a transmedia musical project built around a constructed language written to be sung and generated with Suno Pro; its `.gitignore` forbids audio in git, which makes a sidecar's portability a requirement rather than a slogan. Four discovery takes of *Liora* (3,650,777 / 3,548,907 / 4,286,810 / 4,097,358 B) were stamped at commit [`b8837a9`](https://github.com/cazucito/echo-language/commit/b8837a9) by a 526-line stdlib stamper (531 after the fixes in [`2232272`](https://github.com/cazucito/echo-language/commit/2232272), which corrected a `USLT` decoder that returned the frame's content descriptor instead of the lyrics and a claims guard that printed its message but exited 1 where three documents promised 2) that parses ID3v2.4 and the C2PA manifest store each take carries in a `GEOB` frame, and refuses a claims file that states a digest, id, size, manifest, model or timestamp. Each record declares `core`, `lineage` and `recipe`, points at the lyric file as parent with `relation: "generation"`, and carries `determinism: "none"`: two takes created in the same second differ in length and bytes. No record carries `state` — no take has been compared or chosen, and `STA-7` would require a transition nobody made (`STA-15` makes silence legal). Two measurements carry the document: the model (`chirp-fenix-t4`) and `generatedAt` are read from the provider's own signed `com.suno.provenance` assertion instead of guessed from a brief that asks for `v5.5`; and the C2PA hard binding — SHA-256 over the file minus the manifest's 13,659-byte exclusion range — recomputes exactly for all four takes while differing from the Variorum digest (`ba774da9…` vs `709d7fe7…` for take 04), which is `C2P-6` demonstrated with bytes rather than argued. Adoption also fired `SCH-10` on the first stamped record and the adopter renamed its scheme to `x-echo-archive`, and exposed two gaps recorded as open questions: `REC-9` assumes a single prompt field where Suno has six, and the lifecycle vocabulary has no `generated` state.
- `docs/case-studies/3d-printerator.md` — the second Phase 3 case study, and the first adopter that builds what it records. The project is a repository of 3D-print solutions (parametric OpenSCAD 2021.01 sources, binary STLs, SLA resin, `designs/<solution>/vN/`); its one record describes the complete v2 two-watch separator (`aw9-d2strap-case-v2-holder.stl`, 374,684 B, `sha256:cf3a7707…`) and lives in the adopter's repository at commit [`faa987c`](https://github.com/cazucito/3d-printerator/commit/faa987c), beside a 290-line stdlib stamper whose claims file may not state a digest or an id. The record declares `core`, `lineage` and `recipe`, and carries `state` — which is core, not a class (`CON-3`) — ending in `rejected`: the design was completed, committed as the version to print, and set aside two days later because a bought TPU bumper solved the problem. The centre of the case study is a measurement: the committed STL and two rebuilds with the declared toolchain hold the same 7,492 triangles exactly and three different digests, because the facet order differs. `determinism: "full"` is therefore unavailable (`REC-13`) and `"none"` would misstate the geometry; the member is absent and the absence is documented. The gap that leaves in `REC-12` is recorded as an open question instead of being patched into a shipped enum on the strength of one measurement.
- `docs/adoption.md` — the guide, written by following its own steps rather than describing them afterwards: the `core` path performed on `instruisto`'s release `github-copilot-agents/v1.1.0`, from `gh release download` through `stamp`, the single hand edit (the conformance declaration, `CORE-7`), `validate` and `show`. It states what `core` requires member by member, where the record goes and what it is named (`CORE-12`, `CORE-13`), why a tag is not a version (`SCH-7`, `SEM-5`), seven ways to get the digest or the timestamp wrong, and which classes may be postponed without making the record a lesser one (invariant 4). §12 covers the case where the artifact is not the producer's own: a stored hash is a claim and not a source, `producer` is the record's creator, and the case study below is where the whole path is walked.
- `docs/case-studies/` — adoption told from the adopter's side rather than from this repository: `README.md` states what every case study must carry (a record committed to the project's own repository, a digest computed from the artifact, a declaration, and the friction), and `software-tools.md` is the first one. The project is a private archive of software curated since 1991 — 58 fichas, a PHP + SQLite site, 91 download rows in its exported inventory — and the case study is about the hardest situation adoption faces: publishing artifacts you did not produce. Its one record describes `Gel86a.zip` (2,520,484 B, `sha256:fc0cadf2…`), fetched back from the live site through the general downloads password and hashed; `unzip -t` reported no errors and the value matched the one the archive's admin panel already stored, so the record confirms a claim the project had only asserted. The other ninety artifacts stay unrecorded because a digest copied out of the catalogue is a claim wearing evidence's clothes ([ADR-0013](docs/adr/ADR-0013-spdx-bridge-points-at-the-sbom.md), applied from the producer's side). The document also records the three decisions the format left to the adopter — the version axis (`8.6`, not `8.6a`, because the archive's own [ADR-011](https://github.com/cazucito/software-tools/blob/main/docs/adr/011-descargas-coleccion-privada.md) splits version from variant), `scheme.authority` pointing at the document that defines the scheme instead of at the site, and `producer` naming the record's creator rather than the binary's vendor.
- `examples/instruisto-release-copilot/` — the two records that guide produced, one per release asset rather than one per release (`ID-9`): `proposal.pdf` (73,506 B, `2605defcf2a7…`) and `syllabus.pdf` (148,743 B, `60d62fe0bbe7…`), both carrying the label `1.1.0` the release already had. Both digests were recomputed from the downloaded assets before the records were written.
- `tests/test_docs.py` — `ReadmeExampleTests`: the README's quick example must be a verbatim copy of a record under `examples/`, so the most-visible page cannot teach a shape the validator rejects (it did: `lineage.parents` as strings, `state.transitions[].actor` as a string).
- `spec/90-extensions/spdx.md` — the fourth extension bridge (`SPDX-1`…`SPDX-8`): a record cites the SPDX 2.3 document that describes the artifact's contents, in `extensions["variorum:spdx"]` (`version`, `document`, optional `element`), and never copies a checksum out of it. This is the first bridge where a foreign checksum *can* equal `artifact.digest` — a file element's `SHA256` (§8.4), or a package checksum whose package is a single blob (Annex K.2.2.3) — so the document states exactly when, and why the package verification code cannot: §7.9 hashes the sorted concatenation of the files' SHA-1 *hex strings*, not the files' bytes. `SPDXRef-DOCUMENT` is refused as an element (a document is not one of the things it describes), the namespace may not carry a `#` (§6.5), and `version` is a closed list because SPDX 3.0 replaced the document model (`spdxId` as an IRI, `namespaceMap`, checksums behind `verifiedUsing`).

### Changed

- **`REC-9` was rewritten.** It said `recipe.prompt` MUST be "the prompt as sent, verbatim, including any system or negative prompt in `parameters`" — a sentence written for a generator with one prompt field. It now says the member holds, verbatim, the value of one field the generator accepts, never a concatenation and never a paraphrase, and that an absent `recipe.promptField` leaves the mapping between `prompt` and the generator's fields unspecified. That last clause is deliberate: making absence mean "the generator has one field" would turn a decision no producer made into a claim, which is the defect ADR-0015 closed for `determinism`.
- `schema/variorum.schema.json` — `recipe.promptField` is typed `string` with `minLength: 1`, and `dependentRequired` binds it to `prompt`. Both clauses are `REC-24`'s, so the schema states the rule instead of adding one.
- `docs/case-studies/echo-language.md` — the `REC-9` question it recorded as open is closed by ADR-0016: the record's reading (lyrics in `prompt`, the other five fields in `parameters`) is now the defined one when it is named, and the record — stamped before the member existed — can add `"promptField": "lyrics"` in one edit in the adopter's repository.
- `README.md`, `spec/vectors/README.md`, `.agents/STATE.md` — 208 vectors in thirteen groups, the `recipe` row now cites `REC-22`…`REC-24`, reference tool 0.9.0.
- `schema/variorum.schema.json` — `recipe.determinism` is documented in a `description` and carries no assertion. `REC-12` is a SHOULD, and an `enum` (or a `type`) there was a MUST in disguise: a standard JSON Schema validator rejected a record that `CON-8` calls conformant. The four-grade vocabulary is stated in the description and enforced as a warning by the reference tool.
- `docs/case-studies/3d-printerator.md` — the `REC-12` gap it recorded as open is closed by ADR-0015; the record's absence is dated to its stamping (the grade did not exist yet) instead of being presented as the standard's current answer.
- `README.md`, `spec/vectors/README.md`, `.agents/STATE.md` — 204 vectors in thirteen groups, the `recipe` row cites `REC-22`, reference tool 0.8.0.
- `schema/variorum.schema.json` — `extensions["variorum:prov"]` is typed: a required `version` fixed to `"2013"`, and no member beyond it. The claim is deliberately closed, because `PROV-3` refuses a `document`, an `entity` or a `checksum` and the schema can say so without a rule.
- `spec/vectors/exemptions.json` — `PROV-4`, `PROV-5` and `PROV-6` exempted with reasons: whether a reader treated `prov:value` as the digest, whether a derivation's `prov:type` named one of the eight relations, and whether an invalidation or an attribution was read as a `state` transition or a signature are all conclusions outside the record.
- `spec/00-overview.md` §8 and `spec/90-extensions/README.md` — PROV moves from "planned" to written, and the overview row now says what the bridge actually does: a record projects onto a PROV instance member by member, rather than being called a serialisation of a subset nobody had written down. `spec/vectors/README.md` lists the `prov` group; `README.md` moves to 200 vectors in thirteen groups.
- `docs/case-studies/` — the three "What a consumer can check" blocks now say the reference command runs in a checkout of this repository: the paths in those blocks are relative to the adopter's repository, and the two are never the same directory. `echo-language.md` also states the lyric comparison for the takes where it holds — 667 characters in takes 02–04, 709 in take 01, whose `USLT` frame repeats the final `[Outro]` section — and quotes the adopter's stamper at its corrected length, with the fix commit named.
- `README.md` — the "Quick example" is now a real record, copied verbatim from [`examples/la-enpenso-shot-01/`](examples/la-enpenso-shot-01/), instead of an invented skeleton whose `lineage.parents` were strings and whose `state.transitions[].actor` was a string — both shapes the validator rejects. The field table's first row now names `artifact` and its derived `id`, the members that exist; `identity` was a section title, not a member.
- `schema/variorum.schema.json` — `extensions["variorum:spdx"]` is typed: `version` fixed to `"2.3"`, `document` an absolute URI with no fragment, `element` an `SPDXRef-` identifier that is not `SPDXRef-DOCUMENT`, and no member beyond the three the bridge defines.
- `spec/vectors/exemptions.json` — `SPDX-7` and `SPDX-8` exempted with reasons: comparing a file element's checksum and refusing to read a verification code as an artifact identifier are both obligations on a consumer that holds the artifact and the document.
- `schema/variorum.schema.json` — `extensions["variorum:swhid"]` is typed: an object with `swhid` required and no other member, the identifier pattern kept byte-for-byte in step with the tool's regex, and a `not` guard against fragment qualifiers. The qualifier *combinations* of `SWH-4` depend on the object type and on the other qualifiers; JSON Schema cannot express them, so the reference tool enforces them and the schema says so.
- `CON-9` — a vector carrying `bridge` is obligatory only of implementations that claim that bridge; every other implementation skips it instead of failing it.
- `schema/variorum.schema.json` — `extensions["variorum:c2pa"]` is typed: an object with `manifest` and `location` required, `uri` required exactly when `location` is `external` and forbidden otherwise, and no members beyond the three the bridge defines.
- `CON-24` — coverage now counts every rule identifier defined under `spec/90-extensions/`, not only sections 00–06; `conform --coverage` and CI follow.
- `schema/variorum.schema.json` — `extensions["variorum:semver"]` is now typed (an object, with an optional string `tag`), mirroring `SEM-1` and `SEM-5`.
- `validate` now separates errors (violated MUST) from warnings (violated SHOULD); only errors make a record non-conformant. Checks affected: ID-12, CORE-10, REC-5, REC-12, SCH-10.
- `scheme.name` accepts any lowercase name (SCH-2) in the schema and the reference tool; the previous closed enumeration rejected names the specification already allowed.
- The two examples that declared `lineage` without carrying a `lineage` member now declare what they actually contain.
- `spec/00-overview.md` points class definitions at section 07; extensions may use an unprefixed name, with a warning rather than a rejection.

### Fixed

- **The schema turned `REC-12` from a SHOULD into a MUST.** `recipe.determinism` was typed as `{"enum": ["none", "seeded", "full"]}` while `REC-12` says SHOULD, so a record carrying `"determinism": "maybe"` — conformant by `CON-8` — was rejected by any standard JSON Schema validator and only warned by the reference tool. The schema now documents the grades and asserts nothing; `tests/test_schema.py` fails if an assertion comes back.
- **`SEM-1` read an explicit JSON `null` claim as no claim.** `validate_semver_bridge` fetched the extension with `extensions.get(...)` and returned early when the value was `None`, which is what a missing key returns too, so a record carrying `"variorum:semver": null` skipped every SemVer rule. The four bridges written after it (`C2P-1`, `SWH-1`, `SPDX-1`, `PROV-1`) test key membership and reject `null`, and the schema types all five claims as objects. `SEM-1` already said "When present, its value MUST be an object", so this is the implementation catching up with the rule, not a rule change. `semver/claim-must-not-be-null` is the vector; `SemverBridgeTests.test_claim_must_be_an_object` now covers five non-object claims.
- `variorum validate <directory>` — `load_record` caught a JSON decode error but not a path that is not a file, so a directory or a missing path ended in an `IsADirectoryError`/`FileNotFoundError` traceback where its own docstring promised a readable error. It now exits 1 with `<path>: not a file`, the sentence `digest` and `stamp` already use, and `RecordLoadingTests` pins both cases.
- `docs/adoption.md` §1 and §9 called `state` a separate conformance class. It is not: `CON-3` places it inside `core` whenever the member is present, and `CON-5` bounds the declaration to `core`, `lineage`, `recipe` and `attestation`. The guide now says so — an adopter that trusted it would declare a class the format does not allow, and `3d-printerator`'s record declares three classes while carrying four sections.
- `show` — `recipe.tool` may be a single object or a chain (`REC-5`; the schema types it as `oneOf`). The command printed `via ?` for the array form, which is a record that conforms. It now renders each tool as `name[/model] [version]`, comma-separated for a chain, and `ShowTests` pins both shapes.
- Schema/tool drift against SCH-2 and CORE-10: a SHOULD was being enforced as a MUST, and a valid scheme name was rejected.

## [0.1.0-draft] — 2026-11-22

First draft. Nothing here is stable.

### Added

- `spec/00-overview.md` — scope, six design principles, conformance classes, terminology, relationship to eight existing standards.
- `spec/01-identity.md` — digest-based identity (`ID-1`…`ID-16`), derived record identifier `urn:variorum:sha256:<hex>`.
- `spec/02-scheme.md` — scheme reference table, eleven reserved scheme names, prohibition on redefining ordering (`SCH-1`…`SCH-9`).
- `spec/03-lineage.md` — eight derivation relations, acyclic graph rules, work-level identity (`LIN-1`…`LIN-13`).
- `spec/04-recipe.md` — `manual` / `build` / `generative` / `hybrid`, honest determinism (`REC-1`…`REC-21`).
- `spec/05-state.md` — seven-state lifecycle, legal transition table, terminal rejection (`STA-1`…`STA-15`).
- `spec/06-attestation.md` — JCS signing over the record minus attestation (`ATT-1`…`ATT-12`).
- `schema/variorum.schema.json` — JSON Schema 2020-12.
- `tools/variorum.py` — reference CLI, standard library only.
- `examples/` — three records built from real artifacts in real projects.

### Known gaps

- No conformance suite or test vectors yet; `validate` implements the rules but nothing proves two implementations agree.
- Attestation signing and verification are specified but not implemented in the CLI (needs a key distribution story first).
- Extension bridges (C2PA, SWHID, SPDX, PROV) are planned, not written.
